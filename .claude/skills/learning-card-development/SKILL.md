# Develop a useful learning card

A card earns its place by changing a decision, explanation, prediction, or verification
the learner can make in their real system. A polished syllabus is not that outcome.
The management skill decides whether and when a card belongs in the queue; this skill
develops its content. Prefer revising the relevant existing card or adding a focused
next step to it over creating a duplicate.

Before writing, read the actual card, direct learner words, attempts, and current code
or authoritative source. Distinguish liking/relevance, use, and demonstrated learning.
Preserve what worked: Rithvik liked “Ship = try it” because it addressed a live
verification problem and the connected system. That explanation is a hypothesis;
the direct preference is evidence. Its breadth is not automatically a defect.

Build one useful entry into the subject:

1. Quote the real experience or gap and name the decision this card should improve.
   Name the layer and relevant component. Never manufacture a learner quote.
2. Trace one causal path through the actual system. Give a compact map when it helps.
   Explain why the mechanism produces the experience, not a list of definitions.
3. Offer one safe way to inspect or try it, what evidence it yields, and what it does
   not prove. Verify every command/path against sources; if unknown, omit or mark it
   for verification. Never guess a plausible path. Prefer existing logs, read-only
   inspection, or a disposable mock; do not turn a lesson into an unrequested release.
4. Include a small prediction and an independent transfer/defense check. Keep the
   answer key separate so it cannot masquerade as independent understanding. Accept
   causal explanations in plain language; supply syntax unless recalling syntax is
   itself the learner's chosen goal. Record uncertainty and partial understanding.
5. Provide an obvious stopping point and optional depth. Let the learner choose
   sources, a visual explanation, or code when helpful. Do not force every medium
   or copy the assistant's entire reply into the card.
   Explain each mechanism once. If the path, exercise, and checks repeat the same
   explanation, collapse them; adaptation can be one short sentence.
6. State how feedback changes the card: too basic → skip/raise depth; too broad →
   isolate the missing link; wrong gap → change the topic/card; build energy → take
   the useful check now and leave the deeper learning open.

Use the [review rubric](rubric.md) before publishing. Content errors, invented user
evidence, unsafe exercises, or claims of mastery without learner evidence veto the
draft. Revise the specific failure, then recheck; do not optimize prose scores alone.
For a ledger-enabled project, record `card_draft` and `card_review`; the management
permit must reference a passing review of the exact description sent to Linear.

Default knobs are experiments: one entry task, one system path, optional depth,
one transfer check. Adjust from actual attempts and feedback. Never claim that a
review score, mock learner, or completed build proves this card taught the person.
